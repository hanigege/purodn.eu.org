RouterOS NAT 回流与防火墙规则备份

RouterOS NAT 回流、端口转发和配套防火墙规则备份。

内网的dst-nat要加外网接口如pppoe-out1#

1. 为什么需要回流？#

当你从内网请求公网 IP 时，ROS 收到包后转发给内网服务器，但服务器发现请求方和自己在同一个网段，会直接把回包传给手机。手机发现自己发给公网 IP 的请求却收到了来自内网私有 IP 的响应，会因为安全机制直接丢弃该包。回流规则通过让 ROS 中转这个“回头包”来解决这个问题。

2. 完整的 ROS NAT 脚本（包含 Web 回流）#

请根据你的实际端口修改 12335 (Web) 和 21 (FTP) 等。#
/ip firewall nat
# --- 基础规则 ---
# 1. 核心上网伪装（必须限制在 WAN 口，防止干扰其他转发）
add chain=srcnat action=masquerade out-interface=pppoe-out1 comment="Standard Internet Access"
# --- 端口转发 (DST-NAT) ---
# 2. Syncthing 转发
add chain=dstnat protocol=tcp dst-port=22000 action=dst-nat to-addresses=10.20.20.4 to-ports=22000 comment="Syncthing TCP"
add chain=dstnat protocol=udp dst-port=22000 action=dst-nat to-addresses=10.20.20.4 to-ports=22000 comment="Syncthing UDP"
# 3. Web 服务转发 (示例)
add chain=dstnat protocol=tcp dst-port=12335 action=dst-nat to-addresses=10.20.20.x to-ports=12335 comment="web"
# 4. FTP 服务转发 (示例)
add chain=dstnat protocol=tcp dst-port=21 action=dst-nat to-addresses=10.20.20.x to-ports=21 comment="vsftpd"
# --- 回流规则 (Hairpin NAT) ---
# 只有当内网访问内网服务器时才触发。建议将所有内网服务器放在一个规则里，或者逐个添加。
# 给 Syncthing 添加回流
add chain=srcnat out-interface=bridge1 src-address=10.20.20.0/24 dst-address=10.20.20.4 protocol=tcp dst-port=22000 action=masquerade comment="Hairpin Syncthing TCP"
add chain=srcnat out-interface=bridge1 src-address=10.20.20.0/24 dst-address=10.20.20.4 protocol=udp dst-port=22000 action=masquerade comment="Hairpin Syncthing UDP"
# 给 Web 服务添加回流 (假设内网 IP 为 10.20.20.5)
add chain=srcnat out-interface=bridge1 src-address=10.20.20.0/24 dst-address=10.20.20.5 protocol=tcp dst-port=12335 action=masquerade comment="Hairpin Web"

3. 操作建议：使用“地址列表”简化回流#

在 NAT 中添加回流规则前，先替换源网段、目标服务器及 LAN 接口名称。RouterOS 7.25.1 的 /ip firewall nat 不接受 connection-nat-state 参数，不能把 filter 链的该匹配器直接用于 NAT。以下回流规则通过源网段、目标服务器和 out-interface=bridge1 限定范围；同一 bridge 内纯二层转发的普通直连流量不经过这些 IP NAT 规则。

如果你有很多内网服务器需要回流，一条条加 srcnat 很麻烦。你可以这样做：

在 IP -> Firewall -> Address Lists 里，把所有内网服务器 IP 加到一个叫 Internal_Servers 的列表。

  1. 操作步骤

请在 WinBox 中按照以下两步配置：

第一步：建立服务器地址列表

在 IP -> Firewall -> Address Lists 中，将你所有需要从内网访问的服务器 IP 加入列表：

Name: Internal_Servers | Address: 10.20.20.4 (Syncthing 服务器)
Name: Internal_Servers | Address: 10.20.20.5 (Web 服务器)
(依此类推，将所有有端口转发需求的内网 IP 都加进去)

第二步：添加全局回流规则

在 IP -> Firewall -> NAT 中添加这一条（确保它在所有 dst-nat 规则之后，但在基础 masquerade 规则之前，或者紧随其后）：#

代码段

/ip firewall nat
add chain=srcnat out-interface=bridge1 src-address=10.20.20.0/24 dst-address-list=Internal_Servers action=masquerade comment="Global Hairpin NAT"

使用 Address List（地址列表） 的方式最为高效，不需要在 NAT 规则里指定端口。

当请求的目标地址匹配列表中的 IP 时，RouterOS 会自动对所有协议（TCP/UDP/ICMP 等）和所有端口执行回流操作。

规则排序 例：#

/ip firewall nat
# ====================
# 第一部分：端口映射 (DSTNAT - 外部访问内网)
# ====================
# 将外部网络 (WAN 列表) 对 80/443 端口的访问，转发给内网服务器 (以你的 10.20.20.10 为例)
add chain=dstnat action=dst-nat dst-port=80,443 in-interface-list=WAN protocol=tcp to-addresses=10.20.20.10 comment="Web Server Port Forward from WAN"
# ====================
# 第二部分：源地址伪装 (SRCNAT - 内网访问外部)
# ====================
# 1. Hairpin NAT (内网回流，必须放在全局伪装之前)
# 作用：确保内网设备通过公网域名访问内网服务器时，数据包能在路由器内部正确折返
add chain=srcnat out-interface=bridge1 action=masquerade src-address=10.20.20.0/24 dst-address-list=Internal_Servers comment="Global Hairpin NAT"
# 2. 全局上网伪装 (全局兜底，必须放在 srcnat 链的最底部)
# 作用：所有从 WAN 列表物理或虚拟接口发出的流量，全部转换并伪装为路由器的公网 IP
add chain=srcnat action=masquerade out-interface-list=WAN comment="Global Internet Masquerade"

以上是可按需裁剪的示例规则。导入前必须替换接口、网段和旁路由地址，并按现有配置核对规则顺序；不要把示例直接整段粘贴到正在运行的生产路由器。

4. 验证 Web 服务#

外网测试：手机关 Wi-Fi，访问域名，确认 Web 正常。

内网测试：手机连 Wi-Fi，访问同一个域名。如果能打开，说明回流配置成功。

5. 配套的防火墙规则，也是我自用的#

特别强调：如果使用了小包优先规则配置，必须停用下面所有配置中的fasttrack-connection 规则#

常见 RouterOS 默认防火墙模板会加入 FastTrack 规则。FastTrack 数据包会绕过部分 Mangle、Queue Tree 等处理；如果依赖这些功能做 QoS 或策略路由，应为相关流量排除 FastTrack。FastTrack 是快速转发路径，不等同于硬件转发卸载。

变更前备份并核对现有防火墙#

add action=add-src-to-address-list address-list=ros_ab_stage2 address-list-timeout=15m chain=input comment="ROS-AB 4 stage2 from stage1" connection-state=new dst-port=3981,2222 in-interface=pppoe-out1 protocol=tcp src-address-list=ros_ab_stage1
add action=add-src-to-address-list address-list=ros_ab_stage1 address-list-timeout=5m chain=input comment="ROS-AB 5 stage1 initial attempt" connection-state=new dst-port=3981,2222 in-interface=pppoe-out1 protocol=tcp

add action=accept chain=input comment="8. Accept ICMP (PMTUD)" in-interface=pppoe-out1 protocol=icmp
add action=drop chain=input comment="9. Drop all other input from WAN" in-interface=pppoe-out1
add action=drop chain=input comment="10. Drop all remaining input"
# ====================
# 转发链 (FORWARD) - 穿过路由器 (外网内网)
# ====================
# 1. 旁路由有效连接豁免（放在 FastTrack 之前；新连接仍由后续规则检查）
add action=accept chain=forward comment="1. Skip FastTrack for sing-box out" src-address=10.20.20.6 connection-state=established,related,untracked
add action=accept chain=forward comment="2. Skip FastTrack for sing-box in" dst-address=10.20.20.6 connection-state=established,related,untracked
# 2. FastTrack 加速（处理正常直连流量）
add action=fasttrack-connection chain=forward comment="3. Fasttrack" connection-state=established,related
# 3. 基础状态放行
add action=accept chain=forward comment="4. Accept established,related,untracked" connection-state=established,related,untracked
# 策略路由 FakeIP invalid 例外：仅放行经 bridge1 转发到 sing-box FakeIP 网段
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 dst-address=198.18.0.0/15 comment="放行经旁路由的 IPv4 FakeIP 转发"
# 策略路由真实 IP invalid 例外：凡经 ROS 策略路由送往旁路由的真实 IP 目标（如 Telegram 网段），回包同样绕过 ROS，必须一并放行，原理见下文“不只是 FakeIP”一节
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 comment="放行经旁路由的真实 IP 转发"
add action=drop chain=forward comment="5. Drop invalid" connection-state=invalid
# 4. 内网正常转发与端口映射放行
add action=accept chain=forward comment="6. Allow bridge1 forward (Internal Outbound)" in-interface=bridge1
add action=accept chain=forward comment="7. Allow DSTNAT (Port Forwarding)" connection-nat-state=dstnat in-interface=pppoe-out1
# 5. 全局兜底拦截 (零信任原则)
add action=drop chain=forward comment="8. Drop all other forward"

转发链 (FORWARD)特别说明：#

第5条“DST-NAT"规则：在 IPv4 的 Forward 链中，我加入了一条 connection-nat-state=dstnat。这确保了你在 IP -> Firewall -> NAT 中做的端口映射能够穿透 forward 的兜底 drop 规则。 内网互通：只要数据包进入 bridge1 接口，就会被 Allow bridge1 forward 捕获并放行，不会受到最后一条 drop 的影响。 这样配置后，局域网直连流量可使用 FastTrack 快速转发；sing-box 相关连接由前置规则排除 FastTrack，以免绕过所需的策略处理。

ipv6防火墙配置#

添加旁路由ip规则版 (mosdns+sb)#

/ipv6 firewall filter
# ====================
# 入站链 (INPUT) - 保护路由器本体
# ====================
add action=accept chain=input comment="1. Accept established,related,untracked" connection-state=established,related,untracked
add action=drop chain=input comment="2. Drop invalid" connection-state=invalid
add action=accept chain=input comment="3. Accept ICMPv6 (Critical for IPv6)" protocol=icmpv6
add action=accept chain=input comment="4. Allow DHCPv6 Client from WAN" dst-port=546 in-interface=pppoe-out1 protocol=udp src-address=fe80::/10
add action=accept chain=input comment="5. Allow bridge1 (Internal Admin)" in-interface=bridge1
add action=drop chain=input comment="6. Drop all not from bridge1" in-interface=!bridge1
# ====================
# 转发链 (FORWARD) - 穿过路由器 (外网内网)
# ====================
# 1. 旁路由有效连接豁免（放在 FastTrack 之前；新连接仍由后续规则检查）
add action=accept chain=forward comment="1. Skip FastTrack for sing-box out" src-address=fd88::6666 connection-state=established,related,untracked
add action=accept chain=forward comment="2. Skip FastTrack for sing-box in" dst-address=fd88::6666 connection-state=established,related,untracked
# 2. FastTrack 加速（处理正常 IPv6 直连流量）
add action=fasttrack-connection chain=forward comment="3. Fasttrack" connection-state=established,related
# 3. 基础状态放行
add action=accept chain=forward comment="4. Accept forward established,related,untracked" connection-state=established,related,untracked
# 策略路由 FakeIP invalid 例外：仅放行经 bridge1 转发到 sing-box FakeIP 网段
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 dst-address=2001:2::198:18:0:0/96 comment="放行经旁路由的 IPv6 FakeIP 转发"
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 comment="放行经旁路由的真实 IPv6 转发"
add action=drop chain=forward comment="5. Drop invalid" connection-state=invalid
# 4. 核心协议与内网放行
add action=accept chain=forward comment="6. Accept Forward ICMPv6" protocol=icmpv6
add action=accept chain=forward comment="7. Allow bridge1 forward (Internal Outbound)" in-interface=bridge1
# --- 暴露内网服务 (注意：替换为实际公网 IPv6 地址后再按需启用) ---
add action=accept chain=forward comment="8. Allow NPM (HTTP/HTTPS)" disabled=yes dst-address=240e::xxxx:xxxx dst-port=80,443 protocol=tcp
add action=accept chain=forward comment="9. Allow Hysteria2/Proxy" disabled=yes dst-address=240e::xxxx:xxxx dst-port=36789 protocol=udp
add action=accept chain=forward comment="10. Allow Shadowsocks" disabled=yes dst-address=240e::xxxx:xxxx dst-port=36789 protocol=tcp
# 5. 兜底拦截 (零信任原则)
add action=drop chain=forward comment="11. Drop all other forward (Protect LAN)"

关键提醒： 修改旁路由的ip为你的ipv6地址 如果你的宽带是动态 IPv6 前缀（PD），服务器的完整 IPv6 地址会变化。这种情况下，不应直接写死 dst-address，而是用地址列表加脚本动态维护——完整做法见文末「IPv6 端口转发：先分清两种情况」的情况一；内网没有公网地址、走 NAT66 的看同节情况二。

IPv4 依靠 NAT，不主动映射外部进不来；但 IPv6 是端到端直通（没有 NAT）。 你在 forward 链中放行 dst-port=80,443，却没有指定目标地址 (dst-address)。一旦启用，这代表公网可以访问你局域网内所有设备的 80 和 443 端口（包括光猫、路由器后台、智能家居、其他电脑等）。

正确做法：必须严格绑定目标服务器的 IPv6 地址（dst-address=服务器IPv6地址），或者通过 MAC 地址自动获取到的 IPv6 后缀。

旁路由环境下的 FORWARD invalid 处理#

RouterOS 官方建议在 input 和 forward 链丢弃 connection-state=invalid 数据包，因此上面的防火墙示例保留了这条规则。某些非对称路由、策略路由或特殊 UDP 流量，可能让连接跟踪把特定数据包标记为 invalid；这需要结合实际路径和规则计数器诊断，不能仅凭应用超时就认定原因。

先查看 invalid 规则计数器是否增长，并结合连接跟踪、路由和抓包定位具体流量：

/ip firewall filter print stats where chain=forward and connection-state=invalid
/ipv6 firewall filter print stats where chain=forward and connection-state=invalid

不要一开始就全局禁用或删除 FORWARD 的 invalid 丢弃规则。若日志确认某条策略路由路径上的流量被误标为 invalid，应按入口、出口（必要时再加目标网段）添加窄范围例外，并放在 invalid 丢弃规则之前；不要对所有来源、所有协议放行 invalid 流量。

下方包含完整 FORWARD 规则的 RouterOS 配置示例，已将对应 FakeIP 例外放在 Drop invalid 之前；请选择与你的接口配置相符的一套导入，避免重复导入多个完整方案。

策略路由到 sing-box FakeIP 的例子#

如果 LAN 客户端访问 FakeIP 时，日志显示流量从同一个 LAN bridge 进入、再从该 bridge 转给 sing-box 网关（例如 in:bridge1 out:bridge1），TCP 后续包可能被连接跟踪标为 invalid。当 Drop invalid 排在 LAN 转发放行前面时，这些包会被丢弃，表现为视频或连接卡住。使用同一 FakeIP 分流的其他应用也可能受影响。

以下规则按本例环境编写：198.18.0.0/15 和 2001:2::198:18:0:0/96 是策略路由到 sing-box 的 FakeIP 网段，LAN bridge 是 bridge1。先核对自己的 FakeIP 网段、路由和接口名称；只有日志确认相同路径后才添加。place-before 会把例外放在 forward 链的 invalid 规则前面：

/ip firewall filter
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 dst-address=198.18.0.0/15 place-before=[find where chain=forward and connection-state=invalid] comment="放行经旁路由的 IPv4 FakeIP 转发"

/ipv6 firewall filter
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 dst-address=2001:2::198:18:0:0/96 place-before=[find where chain=forward and connection-state=invalid] comment="放行经旁路由的 IPv6 FakeIP 转发"

例外只匹配经同一 bridge 转发到指定 FakeIP 网段的 invalid 包；其他 invalid 流量仍由原规则丢弃。但要注意：需要豁免的不止 FakeIP——凡是被策略路由送往旁路由的目标都走同一条不对称路径，真实 IP 目标同样会被误伤，见下一小节。

不只是 FakeIP：策略路由的真实 IP 目标同样中招（实测案例）#

2026-11 实测案例：内网一台 MTProto 代理服务器（Telegram 代理）经 ROS 策略路由到 sing-box 网关访问 Telegram 数据中心的真实 IP，Telegram 客户端显示代理延迟 7861ms。逐段定位后确认与 FakeIP 是同一个机制：客户端的 SYN 经 ROS 送到旁路由网关，但网关与客户端在同一网段，回的 SYN-ACK 二层直达、不经过 ROS，ROS 的连接跟踪始终停在“只见 SYN”的半开状态；客户端随后发出的 ACK 和数据包被判为 invalid，被 Drop invalid 逐个丢弃，只能靠 TCP 按 1 秒、2 秒、4 秒重传，熬到连接跟踪记录过期（约 5 秒）才被放行——每条新连接稳定多花约 6.7 秒。连接一旦建立，后续传输完全正常，所以表现为“能用，但每次新建连接都卡一下”，测速软件测的又恰好是建连时刻，数字格外难看。

结论：FakeIP 网段、Telegram 网段、被单独策略路由的 DNS / 流媒体等真实 IP 网段，走的是同一条路径，豁免不能只按 FakeIP 网段写。与其逐个目标网段添加例外，不如按接口放行：只匹配 connection-state=invalid 且进入、离开都是 LAN bridge 的包。这仍然是窄范围例外——从 WAN 侧进来的 invalid 包入口接口不是 bridge，不受影响；Drop invalid 规则本身保留不动。上面各套完整规则中 FakeIP 例外之后的那条无目标地址的规则（注释“放行经旁路由的真实 IP 转发”）就是它，IPv4、IPv6 各一条，位置必须在 Drop invalid 之前。

修复后同目标实测：首包耗时从约 6.9 秒降到约 0.31 秒。

已有环境只想补这两条规则的，可以用 place-before 直接插到 invalid 丢弃规则之前（bridge 名按自己的环境替换）：

/ip firewall filter
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 place-before=[find where chain=forward and action=drop and connection-state=invalid] comment="放行经旁路由的真实 IP 转发"

/ipv6 firewall filter
add action=accept chain=forward connection-state=invalid in-interface=bridge1 out-interface=bridge1 place-before=[find where chain=forward and action=drop and connection-state=invalid] comment="放行经旁路由的真实 IPv6 转发"

补上通用规则后，前面那条按网段写的 FakeIP 例外在功能上已被覆盖，留着也无妨：它排在前面先匹配，计数器单独走，排查时能一眼看出放行的 invalid 里有多少是 FakeIP、多少是真实 IP。

IPv6 端口转发：先分清两种情况#

IPv6 发布内网服务和 IPv4 不是一回事，先看你家的地址是哪种分法：

  • 情况一：内网设备有公网 IPv6 地址。 运营商通过 DHCPv6-PD 下发前缀，内网每台设备都有全球单播地址（GUA）。这种情况下不做 NAT，只需要在 forward 链按「目标地址 + 端口」放行。难点只有一个：家庭宽带的前缀通常是动态的，前缀一变，服务器的完整地址就变，规则里写死的 dst-address 会失效——解决办法是地址列表 + 脚本维护（我生产机就是这种，下文给全套）。
  • 情况二：内网设备没有公网 IPv6 地址（NAT66）。 内网只用 ULA 私有地址（fd00::/8），只有路由器 WAN 口有公网地址。这时的做法和 IPv4 几乎一样：在 IPv6 的 NAT 表里做 dstnat 端口转发，forward 链放行被转发的连接。

下面还是用前面那台 Syncthing 服务器举例（端口 TCP/UDP 22000）。

情况一：公网前缀直达 + 脚本维护地址列表#

前提：WAN 口的 DHCPv6 客户端已请求前缀并建好地址池（如 externat-pool），LAN 口从池里分配了 /64 地址，内网设备能拿到公网地址。另外，服务器的地址后缀必须稳定：后缀就是服务器全局地址的后 64 位，在服务器上执行 ip -6 addr 看它的全局地址，去掉前缀剩下的就是。后缀一般由网卡 MAC 推导（EUI-64）或由系统固定生成；如果服务器开了会变动的「临时地址/隐私扩展」，先关掉或改成固定后缀，否则脚本算不准。

第一步：给要发布的服务器建一个地址列表，只放它一个地址（先用 ::1/128 占位，脚本会改成真实地址）：

/ipv6 firewall address-list
add list=published-srv-v6 address=::1/128 comment="脚本维护，勿手改"

第二步：forward 链放行。注意 dst-address-list 绑的是上面的列表，不是写死地址；place-before 保证它排在兜底 drop 之前（接口列表版把 in-interface 换成 in-interface-list=WAN、out-interface 换成 out-interface-list=LAN 即可）：

/ipv6 firewall filter
add chain=forward action=accept protocol=tcp dst-address-list=published-srv-v6 dst-port=22000 in-interface=pppoe-out1 out-interface=bridge1 place-before=[find comment="11. Drop all other forward (Protect LAN)"] comment="Publish Syncthing TCP"
add chain=forward action=accept protocol=udp dst-address-list=published-srv-v6 dst-port=22000 in-interface=pppoe-out1 out-interface=bridge1 place-before=[find comment="11. Drop all other forward (Protect LAN)"] comment="Publish Syncthing UDP"

第三步：维护脚本。每分钟从 LAN 口地址取出当前前缀，和固定后缀拼出服务器的完整地址，写回地址列表。池名、前缀、后缀都校验过才动手，任何一步对不上就报错退出、保持原值——宁可暂时打不开，也不能把门开到错误地址上：

/system script
add name=update-published-ipv6 policy=read,write source={
    :local poolName "externat-pool"
    :local lanInterface "bridge1"
    :local suffix [:toip6 "::be24:11ff:fe04:3c5d"]
    :local ids [/ipv6 address find where interface=$lanInterface and from-pool=$poolName]
    :if ([:len $ids] != 1) do={ :log error "published-v6: LAN prefix not found"; :error "no prefix" }
    :local text [/ipv6 address get $ids address]
    :local prefix ([:toip6 [:pick $text 0 [:find $text "/"]]] & ffff:ffff:ffff:ffff::)
    :if (($prefix in 2000::/3) = false) do={ :log error "published-v6: prefix not global"; :error "bad prefix" }
    :local host ($prefix | $suffix)
    :local item [/ipv6 firewall address-list find where list="published-srv-v6"]
    :if ([:len $item] != 1) do={ :log error "published-v6: address list must contain exactly one entry"; :error "bad list" }
    :if ([/ipv6 firewall address-list get $item address] != ([:tostr $host] . "/128")) do={
        /ipv6 firewall address-list set $item address=([:tostr $host] . "/128")
        :log info "published-v6: address updated"
    }
}
/system scheduler
add name=update-published-ipv6 interval=1m start-time=startup on-event="/system script run update-published-ipv6" policy=read,write

脚本里的变量按自己的环境改：poolName 是 DHCPv6 客户端建的地址池名，suffix 是你服务器的地址后缀（示例值是按某块网卡 MAC 推导的 EUI-64，务必换成你自己的）。要发布多台服务器，就每台建一个列表、脚本里多拼几个后缀各写回各的列表，forward 放行规则一组服务器一套。

如果你的前缀是固定的（少数宽带），这一整套脚本都不需要，直接把服务器的 /128 地址写进前面模板里那几条 disabled 示例的 dst-address、启用即可。

情况二：NAT66（内网只有 ULA 地址）#

前提：LAN 口分配 ULA 网段（如 fd88::/64），服务器固定一个 ULA 地址（如 fd88::10），WAN 口有公网 IPv6 地址。配置心智和 IPv4 端口转发完全一致，分三处：

第一步：出站伪装（内网 ULA 出网靠它；如果已经有了不要重复加）：

/ipv6 firewall nat
add chain=srcnat out-interface=pppoe-out1 action=masquerade comment="NAT66 Internet Access"

第二步：端口转发。WAN 地址稳定时可以再加 dst-address=你的WAN公网地址 限定目标；WAN 地址是动态的就只按入口接口匹配：

/ipv6 firewall nat
add chain=dstnat protocol=tcp dst-port=22000 in-interface=pppoe-out1 action=dst-nat to-addresses=fd88::10 to-ports=22000 comment="NAT66 Syncthing TCP"
add chain=dstnat protocol=udp dst-port=22000 in-interface=pppoe-out1 action=dst-nat to-addresses=fd88::10 to-ports=22000 comment="NAT66 Syncthing UDP"

第三步：forward 链放行被 dstnat 的连接（一条通配规则管所有 NAT66 转发，和 IPv4 里那条 Allow DSTNAT 一个道理），排在兜底 drop 之前：

/ipv6 firewall filter
add chain=forward action=accept connection-nat-state=dstnat in-interface=pppoe-out1 place-before=[find comment="11. Drop all other forward (Protect LAN)"] comment="Allow NAT66 DSTNAT"

内网设备用公网域名访问这台服务器时同样需要回流：加一条 srcnat（源是内网 ULA 网段、目标是这台服务器、出接口是 LAN 口），或者更简单——让内网 DNS 直接把域名解析到服务器的 ULA 地址，连回流都不用：

/ipv6 firewall nat
add chain=srcnat src-address=fd88::/64 dst-address=fd88::10 out-interface=bridge1 action=masquerade comment="NAT66 Hairpin"

最后提醒一句：NAT66 不是 IPv6 的推荐用法，它把端到端模型又改回了 NAT，个别对地址敏感的应用可能不正常；运营商给 PD 前缀时优先用情况一。情况二适合只有单个公网地址、或者明确想把内网拓扑藏起来的场景。
