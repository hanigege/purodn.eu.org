Alpine 3.24 生产级 Docker 部署：普通用户从安装到加固的完整流程

在 Alpine Linux 3.24 上给普通用户开通 Docker 的完整生产流程：装包、入组、daemon 加固、每容器安全基线、SSH 收敛、swap 与重启验收。每一步都在真机跑过，附真实报错原文和排查方法。

给普通用户开通 Docker 这件事，网上的教程九成是 Debian/Ubuntu 的，直接照抄到 Alpine 上会连第一步都过不去——Alpine 没有 systemctl、没有 usermod、没有 service，连 useradd 都是缺的。

这篇把我在一台真实 Alpine 云主机上从零到验收的全过程整理成可复制的流程，每一步都写明：

  • 这条命令在 Alpine 上到底对应什么
  • 哪些值最容易抄错
  • 跑完怎么验证它真的生效了（不是"看起来配好了"）
  • 失败时报错原文长什么样，对应什么原因

⚠️ 先说结论：docker 组等于 root。这不是配置失误，是 Docker 的设计——能访问 /var/run/docker.sock 的人可以起一个挂载宿主根目录的容器，直接读写整台机器。所以"生产级"的重点不是让普通用户拿不到 root，而是只让可信账号进组 + 限制每个容器能干什么。

一、开工前：摸清系统底数

先确认这台机器到底是什么，别糊里糊涂开始装。

cat /etc/os-release | head -3
uname -m
nproc
free -m | head -2
df -h /
ls /sys/kernel/security/lsm

要看的四项：

项目怎么看判断
发行版/etc/os-release 的 ID + VERSION_ID必须是 alpine，记下版本号（3.24 / 3.23 包名一样，3.19 以下可能不同）
架构uname -maarch64 = ARM 云主机，x86_64 = 常规。后面拉镜像默认会拉对架构，但自己写 --platform 时要注意
内存/CPUnproc、free -m1 核 2G 的机器别计划跑一堆 Java 服务
安全模块/sys/kernel/security/lsmAlpine 默认没有 AppArmor、没有 SELinux，只有 capability,landlock,yama。意味着容器隔离只能靠 seccomp + cap_drop + 不用 privileged

我这次的环境（后文所有报错和输出都来自这台机器）：

  • Alpine Linux v3.24.3，内核 6.18.58，aarch64，1 vCPU / 5.9 GiB 内存 / 45 GiB 盘
  • 系统里已经装了 docker 包，但服务没启动、没进开机自启、连 /etc/docker/ 目录都不存在——这是最常见的状态：包装了，但等于没配

💡 提示：apk info -e docker 只能证明包在，不能证明服务在跑。判据永远是 rc-service docker status 和 docker ps 能不能连上 socket。

二、装 Docker：Alpine 的包名和 Debian 不一样

apk update
apk add docker docker-cli-compose

装完会自动带进来这些（不用单独装）：

  • docker-engine（dockerd 本体）、docker-cli（命令行）
  • containerd、runc（运行时）
  • docker-cli-buildx、docker-cli-compose（CLI 插件）
  • docker-openrc（OpenRC 服务脚本）

这里最容易抄错的两个地方：

  1. docker compose 中间是空格，不是横线。 网上老教程让你 apk add docker-compose，那是 Python 写的 compose v1，早就停止维护；Alpine 3.24 里应该装 docker-cli-compose，调用方式是 docker compose up -d。
  2. docker 是元包，docker-cli 只是客户端。 只装 docker-cli 的话 docker ps 会报连不上 socket，因为根本没有守护进程。

验证：

docker --version
docker compose version

正常输出类似：

Docker version 29.9.2, build a82e528
Docker Compose version v5.6.1

三、启动服务 + 开机自启（Alpine 没有 service 命令）

rc-service docker start
rc-service docker status
rc-update add docker default

三条命令分别对应：启动、看状态、加进开机自启。

报错原文对照：

-sh: service: not found
-sh: systemctl: not found

Alpine 用的是 OpenRC，不是 systemd。所有教程里的 service docker restart、systemctl enable docker 在这里全部失效。对应关系：

Debian/UbuntuAlpine
systemctl start dockerrc-service docker start
systemctl restart dockerrc-service docker restart
systemctl enable dockerrc-update add docker default
systemctl is-enabled dockerrc-update show default | grep docker
journalctl -u dockertail -50 /var/log/docker.log

⚠️ 最容易漏的一步：rc-service docker start 只是这次启动，重启机器就没了。必须 rc-update add docker default。我在验收时专门重启了两次整机来确认——第一次就是因为漏了这步，重启后 Docker 没起来。

判断 docker 到底活没活，别看 rc-service status 显示 started 就完事，直接跑：

docker ps

如果报下面这个，说明守护进程没起来或者 socket 不存在：

failed to connect to the docker API at unix:///var/run/docker.sock; check if the path is correct and if the daemon is running: dial unix /var/run/docker.sock: connect: no such file or directory

先看日志：

tail -50 /var/log/docker.log

Alpine 上 dockerd 的日志在文件里，不在 journalctl。

四、让普通用户能用 Docker（验证必须开新会话）

假设你的普通用户名是 test（后文都用 test，换成你自己的）：

addgroup test docker
id test

id 的输出里要能看到 103(docker) 这样的组（数字是 Alpine 上 docker 组的 gid，各家系统可能不同，看名字即可）：

uid=1000(test) gid=1000(test) groups=1000(test),10(wheel),103(docker)

常抄错的值：

  • ❌ usermod -aG docker test —— Alpine 上默认没有 usermod，会报 usermod: not found（除非额外装了 shadow 包）
  • ✅ addgroup test docker —— Alpine 的语法是"把用户加进组"，参数顺序和 usermod 相反，特别容易写反
  • ⚠️ 顺序写反成 addgroup docker test 会创建一个叫 test 的新组，不报错，但什么也没生效

验证方式决定成败。 组权限只对新会话生效，当前 shell 里直接 docker ps 会报：

permission denied while trying to connect to the docker API at unix:///var/run/docker.sock

正确的验证是退出重登，或者直接开一条新 SSH：

ssh test@203.0.113.10 'id; docker ps'

看到 docker ps 输出表头（哪怕是空的 CONTAINER ID IMAGE ...）才算成功。

💡 提示：newgrp docker 也能让当前 shell 立刻拿到组，但那是临时糊弄自己——脚本、cron、systemd/OpenRC 服务启动的进程都拿不到。生产验证一律用新会话。

五、daemon.json：三行配置挡掉最常见的三类事故

配置文件固定是 /etc/docker/daemon.json（不是 config.json，不是 daemon.conf）。

mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'JSON'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "100m", "max-file": "3" },
  "live-restore": true,
  "no-new-privileges": true
}
JSON

三个键各自解决一个真实问题：

配置解决什么不配的后果
log-opts 限额防单个容器把日志写满根盘一个刷日志的容器能让整台机器磁盘 100%，SSH 都登不上
live-restoredockerd 升级/重启时容器继续跑每次 rc-service docker restart 全部业务中断
no-new-privileges禁止容器内进程通过 setuid 提权容器里带了 setuid 二进制（su、sudo）就能在容器内提权

改完必须干跑校验，别直接重启：

dockerd --validate --config-file=/etc/docker/daemon.json

合法输出只有一句：

configuration OK

写错键名的报错原文（这是 Docker 29 的行为，未知键直接拒绝启动）：

unable to configure the Docker daemon with file /etc/docker/daemon.json:
the following directives don't match any configuration option: <你的错误键名>

这条干跑能在重启前拦住几乎所有"改完 docker 起不来"的事故。

然后重启 + 确认真的生效（不是配置文件写对了就行）：

rc-service docker restart
docker info | sed -n '/Security Options/,/Kernel Version/p'

要看到 no-new-privileges 出现在列表里：

 Security Options:
  seccomp
   Profile: builtin
  cgroupns
  no-new-privileges

再验证容器默认确实带上了这个限制：

docker run --rm --entrypoint sh alpine:3.20 -c 'grep NoNewPrivs /proc/self/status'

输出 NoNewPrivs: 1 才对。

⚠️ 这两件事不要做：

  1. 不要 chmod 750 /etc。很多"安全加固清单"里有这条，但它是无效动作：目录的 r 位管"能不能列出内容"，x 位管"能不能穿过"，750 保留了 x，非 root 照样能读 /etc/ssh/sshd_config 这类已知路径。副作用倒是实打实的：非 root 无法 ls /etc、无法 glob /etc/*.conf，会莫名弄坏 apk 和备份脚本。/root 默认就是 700，也不用改。
  2. 不要开全局 privileged，也不要在 compose 里给单个容器 privileged: true。这是把整台机器的控制权直接交出去，比什么加固都致命。

六、userns-remap 要不要开？（实测代价表）

网上很多教程会把 "userns-remap": "default" 说成"生产必备"。它确实有用，但在 Alpine 上有额外门槛，而且代价不小。先看它实际做了什么。

开启后容器内的 root 会映射成宿主机的高位 UID：

$ docker exec <容器> cat /proc/self/uid_map
         0     100000      65536
$ ps -eo pid,user,args | grep 容器进程
  8549 100000  ...

它防的是容器内的漏洞逃逸后直接拿到宿主机 root。但它不防“普通账号被拿到”——能调 docker socket 的人一句 docker run --userns=host -v /:/host ... 就绕回去了（--userns=host 是官方支持的单容器豁免，实测可用）。

Alpine 上开它会先撞两个坑：

Error during "dockremap" user creation: error adding user "dockremap":
cannot add user; no useradd/adduser binary found

Alpine 只有 busybox 的 adduser，dockerd 要的是 useradd。装 shadow 包能解决：

apk add --no-cache shadow

但接着撞第二个，而且更隐蔽——dockerd 会无限重启，rc-service status 短暂显示 started，socket 却不存在：

error creating ID mappings: open /etc/subuid: no such file or directory

Alpine 的 shadow 不会自动写 /etc/subuid、/etc/subgid，必须手工补：

echo "dockremap:100000:65536" >> /etc/subuid
echo "dockremap:100000:65536" >> /etc/subgid

开了之后的真实代价（逐项实测）：

行为结果
容器内 root 在宿主的 UID100000（正常）
容器内绑 80 端口✅ 可以（netns 属于该 userns，能力有效）
宿主 -p 80:80 发布✅ 可以（由 dockerd 以 root 绑定）
--network host❌ cannot share the host's network namespace when user namespaces are enabled
--privileged❌ privileged mode is incompatible with user namespaces
bind mount 写入文件容器内是 0:0，宿主看到 100000:100000，备份脚本读不了
存储驱动退回 overlay2（日志原文：userns remapping enabled, disabling containerd snapshotter）
性能用户命名空间本身零开销；影响性能的是 bridge 还是 host 网络，与 remap 无关

结论（按场景选）：

  • 单管理员、自己写配置、已经能 root 的机器 → 不必开。省下的运维复杂度比那层保险值钱。
  • 公网暴露的多容器栈、多人维护、跑别人的代码 → 值得开，但要接受"host 网络必须例外"这一条（比如 TURN 服务器）。

如果要回滚：

rm /etc/docker/daemon.json     # 或者删掉 userns-remap 那一行
rc-service docker restart
rm -rf /var/lib/docker/100000.100000

⚠️ 开和关都会让原有容器/镜像在新命名空间下不可见。启用前先确认机器上没有要保留的运行中栈。

七、每个容器的安全基线（compose 模板）

daemon.json 管的是全局，容器层面的限制要写在 compose 里。这套模板可以直接抄：

services:
  你的服务:
    image: 固定版本号，别用 latest
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    pids_limit: 200
    mem_limit: 512m
    volumes:
      - type: volume
        source: 服务名_data
        target: /data
volumes:
  服务名_data:

四个限制的作用：

  • cap_drop: [ALL] —— 容器默认能拿一堆 Linux capability，全砍掉，需要哪个再 cap_add 单独加
  • pids_limit —— 防 fork 炸弹；1 核小机器上这个尤其重要
  • mem_limit —— 防单个容器吃光内存触发 OOM，把整台机器的 SSH 一起拖死
  • no-new-privileges:true —— 和全局那条一样，写在容器层做双保险

铁律三条：

  1. 任何容器都不挂 /var/run/docker.sock。这是最常见的"把 root 递给容器"的方式，CI、监控、Watchtower 类工具最爱这么干。
  2. 不用 privileged: true，不用 cap_add: [SYS_ADMIN]。
  3. 数据用 named volume，不要 bind mount 到 /home。bind mount 会让容器内的 UID 直接写你的家目录，权限一乱就很难收拾。

需要 host 网络的服务（TURN、VPN、抓包类）单独列一份例外清单，写清理由。默默放开是最容易出事的做法。

八、SSH 加固：比容器隔离值钱得多

很多人（包括我自己一开始）以为"只能用密钥登录"是默认的。不是。

判断方法只有一个——看 sshd 的有效配置，不是看配置文件里写了什么：

sshd -T | grep -Ei 'passwordauthentication|kbdinteractive|permitrootlogin'

改之前我拿到的输出是：

permitrootlogin prohibit-password
passwordauthentication yes
kbdinteractiveauthentication yes

passwordauthentication yes 是 OpenSSH 的默认值，配置文件里没显式写就一直是开的。如果账号有密码（passwd -S test 显示 P），公网 22 端口就能被密码爆破。

加固配置（Alpine 的 sshd_config 顶部有 Include /etc/ssh/sshd_config.d/*.conf，新文件会优先生效）：

mkdir -p /etc/ssh/sshd_config.d
cat > /etc/ssh/sshd_config.d/99-hardening.conf <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
PermitRootLogin prohibit-password
MaxAuthTries 3
LoginGraceTime 20
ClientAliveInterval 300
ClientAliveCountMax 2
AllowAgentForwarding no
AllowTcpForwarding no
X11Forwarding no
PermitUserEnvironment no
EOF

改之前先确认两件事，否则会把自己锁在外面：

  1. 你的公钥已经在 ~/.ssh/authorized_keys 里
  2. 你当前这条连接就是用密钥登录的（不是密码登录后还没来得及配密钥）

然后语法校验 + 平滑重载（不会断开现有连接）：

sshd -t
rc-service sshd reload

sshd -t 没有任何输出就是通过。

验证密码认证确实关掉了，看报错里的认证方法列表：

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no test@203.0.113.10 true

改之前是：

Permission denied (publickey,password).

改之后应该只剩 publickey：

Permission denied (publickey).

括号里的方法列表就是最硬的证据。

这一步有多必要？ 我这台机器上线几个小时，/var/log/messages 里已经记录了 73 次真实爆破尝试（Invalid user mongodb、Invalid user admin、Invalid user azure…），来自两个境外 IP，全部是自动扫描。密码关掉之后这些连接在认证阶段就被拒绝，连"猜密码"的机会都没有。

可选：sshguard 自动封禁

Alpine 的 sshguard 包有个大坑：它只提供二进制，没有 init 脚本、没有默认配置，而且不会自己建 iptables 链。

直接 apk add sshguard 然后启动，会得到"进程在跑但什么都不封"的假象，日志里反复出现：

iptables: No chain/target/match by that name.

原因是它的 sshg-fw-iptables 只执行 iptables -I sshguard -s <ip> -j DROP（链名小写），链必须你自己先建。

第二个坑是日志源：Alpine 的 busybox syslogd 默认没开环形缓冲，logread -F 会报：

logread: can't find syslogd buffer: No such file or directory

所以配置要改成直接 tail 日志文件：

cat > /etc/sshguard.conf <<'EOF'
BACKEND="/usr/libexec/sshg-fw-iptables"
LOGREADER="/usr/libexec/sshg-logtail /var/log/messages"
WHITELIST="127.0.0.1/8 ::1"
THRESHOLD=40
BLOCKTIME=1200
DETECT_LIMIT=40
PIDFILE="/run/sshguard.pid"
EOF

服务脚本要用 supervise-daemon（用 command_background=true 会被判定成启动后立即停止），并且在 start_pre/start_post 里保证链存在：

cat > /etc/init.d/sshguard <<'EOF'
#!/sbin/openrc-run
supervisor=supervise-daemon
name="sshguard"
command="/usr/sbin/sshguard"
respawn_delay=10
respawn_max=0
output_log="/var/log/sshguard.log"
error_log="/var/log/sshguard.log"

depend() { need net; after firewall docker; }

ensure_chain() {
    iptables -N sshguard 2>/dev/null
    iptables -C INPUT -j sshguard 2>/dev/null || iptables -I INPUT 1 -j sshguard
    ip6tables -N sshguard 2>/dev/null
    ip6tables -C INPUT -j sshguard 2>/dev/null || ip6tables -I INPUT 1 -j sshguard 2>/dev/null
    return 0
}
start_pre() { ensure_chain; }
start_post() { sleep 1; ensure_chain; }
stop_post() {
    iptables -D INPUT -j sshguard 2>/dev/null
    ip6tables -D INPUT -j sshguard 2>/dev/null
    return 0
}
EOF
chmod +x /etc/init.d/sshguard
rc-service sshguard start
rc-update add sshguard default

验收判据（不要用自己的公网 IP 去试，会把自己封掉）：

iptables -S | grep -i sshguard

要看到这两行，以及真实攻击源被写进去：

-N sshguard
-A INPUT -j sshguard
-A sshguard -s 203.0.113.66/32 -j DROP

💡 提示：rc-service sshguard restart 会清空已学到的封禁记录，重启后要等新的攻击事件重新积累。这是正常现象。

九、加 swap：Alpine 有个隐藏坑

内存小于 8G 的机器跑 Python 类服务（比如 Synapse）最好加 swap，否则一次内存峰值就可能被 OOM 杀掉进程。

dd if=/dev/zero of=/swapfile bs=1M count=2048 2>/dev/null
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile

然后写进 fstab，并设一个保守的 swappiness：

echo '/swapfile none swap sw 0 0' >> /etc/fstab
mkdir -p /etc/sysctl.d
echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
sysctl -w vm.swappiness=10

这里是 Alpine 独有的坑：fstab 写了不等于生效。 Alpine 的 swap 服务默认不在任何 runlevel，重启后 /proc/swaps 只剩一个表头，swapfile 白占 2G 磁盘。必须补：

rc-update add swap boot

验证：

cat /proc/swaps

要有 /swapfile 这一行：

Filename        Type      Size      Used  Priority
/swapfile       file      2097148   0     -2

十、整机重启验收（唯一可信的验收）

配置全做完之后，重启一次。这不是走形式——我在这一步实际发现了两个问题：swap 没自启、sshguard 的 iptables 链没建起来。不重启永远发现不了。

reboot

等机器回来，逐项跑：

# 1. 服务是否自启
rc-update show default | grep -E 'docker|sshd|sshguard'
rc-update show boot | grep swap

# 2. docker 是否在跑、安全选项是否正确
rc-service docker status
docker info | sed -n '/Security Options/,/Kernel Version/p'

# 3. 普通用户免 sudo
docker ps

# 4. sshd 是否仍然只认密钥
sshd -T | grep -Ei '^(passwordauthentication|kbdinteractive)'

# 5. swap 是否挂上
cat /proc/swaps

# 6. sshguard 链是否在
iptables -S | grep -i sshguard

六个项目全过才算交付。任何一项没过，回去看对应章节。

⚠️ 启动顺序的坑：刚重启完那一两分钟，sshguard 的链可能还没来得及建（服务并行启动）。等 1-2 分钟再查，别急着下结论。

十二、最后：这份清单的取舍

这套流程没有任何一步是"因为安全所以安全"的仪式，每条都对应一个真实会在生产里咬人的场景：

  • 日志限额 → 一个死循环刷日志的容器，能把整台机器写挂
  • live-restore → 升级 dockerd 时业务不中断
  • 只让可信账号进 docker 组 → 这是唯一真正有效的边界（因为组权限本身就是 root）
  • 每容器 cap_drop + mem_limit + 不挂 socket → 挡住 90% 的"容器变跳板"路径
  • SSH 只认密钥 → 公网爆破是持续性的，不是偶发
  • 重启验收 → 所有"配好了"的错觉，只有重启能戳破

至于 userns-remap 这种更重的隔离手段，要不要上取决于你的威胁模型：单人维护、账号本身就有 root 的机器，收益有限、代价不小；公网暴露的多容器栈，值得上，但要提前想清楚 host 网络例外怎么处理。
