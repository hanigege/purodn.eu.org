tssh+tsshd 实战：通过 SOCKS5/Hysteria2 连接 TCP 被阻断的服务器

从 VNC 救援、安装 tsshd、配置备用 SSH 端口，到通过内网 sing-box 的 SOCKS5 和 Hysteria2 使用 tssh，并自动进入 tmux。

有些 VPS 的 22 端口并不是服务器本机防火墙拒绝，而是公网链路上的 TCP 被阻断。这时直接运行 ssh root@服务器IP 往往只会超时；如果服务器还保留着网页 VNC，就可以先从 VNC 进入系统，安装 tsshd，再让 tssh 把 SSH 会话切换到更适合不稳定网络的传输层。

本文记录一套适合小白照着做的方案：

Mac
  │ SSH 初始连接：通过 ProxyCommand
  ▼
内网 sing-box SOCKS5
  │ Hysteria2 出站
  ▼
远程服务器：备用 SSH 端口 2222
  │ tssh 启动 tsshd
  ▼
tmux 持久终端

这套方案有一个关键认识：tssh --udp 仍然需要先完成一次普通 SSH 登录，然后才启动远端 tsshd。如果本机没有任何可用的 TCP 引导路径，单独安装 tsshd 并不能让它凭空绕过 TCP 阻断。官方文档也明确描述了这个启动顺序：tsshd 工作原理。

一、先判断问题在哪里

先在客户端测试普通 SSH：

ssh -p 22 root@203.0.113.10

如果提示 Connection refused，通常是目标端口没有服务监听；如果长时间 i/o timeout，更像是上游链路、云防火墙或系统防火墙丢弃了数据包。不要只测试 22，也测试一个确定开放的 HTTPS 端口：

nc -vz -G 5 203.0.113.10 22
nc -vz -G 5 203.0.113.10 443

如果 22、443 和自定义 SSH 端口都超时，说明问题很可能不在 sshd_config 的某一行，而在到这台 IP 的 TCP 路径上。此时可以使用 VPS 控制台提供的网页 VNC 登录服务器。

本文中的 203.0.113.10、10.0.0.6 和端口都是示例，请替换成自己的地址；不要把真实公网 IP、内网 IP、用户名、密码或私钥写进公开文章。

二、通过网页 VNC 进入服务器

网页 VNC 只是一条应急管理通道。登录后先确认系统、网卡和默认路由：

cat /etc/os-release
ip -4 addr show scope global
ip route

再确认 SSH 是否正在监听：

ss -lntp | grep -E ':(22|2222)\b' || true
systemctl status ssh ssh.socket --no-pager

如果 Ubuntu 使用了 ssh.socket 的 socket activation，只修改 /etc/ssh/sshd_config 里的 Port 可能不会让新端口真正监听。后面会同时处理 sshd_config 和 ssh.socket。

三、安装 tsshd

先在 tsshd GitHub Releases 查看最新版本和文件名。下面以 64 位 Linux 为例：

TSSHD_VERSION=0.1.10
cd /tmp
curl -fL -o tsshd.tar.gz \
  "https://github.com/trzsz/tsshd/releases/download/v${TSSHD_VERSION}/tsshd_${TSSHD_VERSION}_linux_x86_64.tar.gz"
tar -xzf tsshd.tar.gz
sudo install -m 0755 tsshd /usr/local/bin/tsshd
/usr/local/bin/tsshd --version

实际使用时，把 TSSHD_VERSION 换成 Releases 页面上的当前版本。看到类似下面的输出，说明二进制已经安装：

trzsz sshd 0.1.10

tsshd 不需要单独作为一个长期 systemd 服务运行。正常情况下，它由 tssh --udp 登录时通过 SSH 临时启动，每个登录会话对应一个独立进程。

四、给 SSH 增加备用端口

这里使用 2222 作为备用 SSH 端口，原来的 22 可以保留，方便以后排查。

创建 SSH 配置片段：

sudo tee /etc/ssh/sshd_config.d/99-tssh-port.conf >/dev/null <<'EOF'
Port 2222
EOF

先检查配置语法：

sudo sshd -t

如果服务器使用 ssh.socket，创建 socket override：

sudo mkdir -p /etc/systemd/system/ssh.socket.d
sudo tee /etc/systemd/system/ssh.socket.d/override.conf >/dev/null <<'EOF'
[Socket]
ListenStream=
ListenStream=0.0.0.0:22
ListenStream=[::]:22
ListenStream=0.0.0.0:2222
ListenStream=[::]:2222
EOF

重新加载并重启 socket：

sudo systemctl daemon-reload
sudo systemctl restart ssh.socket

确认 22 和 2222 都在监听：

ss -lntp | grep -E ':(22|2222)\b'

如果你的发行版没有 ssh.socket，不要照搬 socket override；只保留 sshd_config.d 配置，然后重启对应的 ssh 或 sshd 服务即可。

五、放行 tsshd 的端口

本文固定使用 61001，这样排查时比较直观。服务端至少需要允许：

TCP 2222   普通 SSH 引导
TCP 61001  tssh 的 TCP 代理模式
UDP 61001  tssh 的原生 UDP 模式

如果使用 UFW：

sudo ufw allow 2222/tcp
sudo ufw allow 61001/tcp
sudo ufw allow 61001/udp
sudo ufw reload

如果使用 nftables，要把规则加入你自己的持久化规则文件，而不是只临时执行 nft add rule。规则的核心形式如下：

tcp dport 2222 accept
tcp dport 61001 accept
udp dport 61001 accept

修改后先验证语法，再加载：

sudo nft -c -f /etc/nftables.conf
sudo systemctl reload nftables

不同服务器的表名和 input chain 名称可能不同，先用下面的命令查看现有规则，避免把规则加到不存在的表里：

sudo nft list ruleset

不要因为云厂商面板显示“全放行”就跳过这一步；系统内部可能仍然有 nftables、iptables 或 firewalld 规则。

六、准备公钥登录

建议使用公钥，不要为了方便打开 root 密码登录。客户端生成一把专用 ED25519 密钥：

ssh-keygen -t ed25519 \
  -f ~/.ssh/tssh_target_ed25519 \
  -C 'tssh-server' \
  -N ''

-N '' 表示私钥没有口令，适合测试，但生产环境更建议给私钥设置口令并交给 macOS Keychain 管理。查看公钥：

cat ~/.ssh/tssh_target_ed25519.pub

通过网页 VNC 或已有的服务器控制台，把整行公钥追加到服务器：

mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo '把客户端的整行 ssh-ed25519 公钥粘贴到这里' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

服务器端可以继续关闭密码认证：

PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes

修改后用 sshd -t 检查，再重载 SSH 服务。不要在还没有验证公钥登录前关闭 VNC 或现有 SSH 会话。

七、让内网 sing-box 提供 SOCKS5

如果 Mac 不能直接连接目标服务器，但内网有一台 sing-box 客户端已经通过 Hysteria2 出站，那么可以在这台客户端上增加一个仅监听内网的 SOCKS5 入站：

{
  "type": "socks",
  "tag": "ssh-socks",
  "listen": "10.0.0.6",
  "listen_port": 1080
}

然后给这个入站配置到现有代理出站的路由。出站 tag 要替换成你自己配置中的名字，例如：

{
  "type": "field",
  "inbound": ["ssh-socks"],
  "outbound": "proxy"
}

不要把 SOCKS5 监听到公网；只绑定内网地址，并在防火墙中限制来源。配置完成后按你当前 sing-box 的方式校验并重载：

sing-box check -c /etc/sing-box/config.json
sudo systemctl reload sing-box

先从 Mac 测试 SOCKS5 是否真的能连接服务器的备用 SSH 端口：

nc -v -x 10.0.0.6:1080 -X 5 203.0.113.10 2222

如果看到 succeeded，说明 TCP 引导路径已经打通。

八、升级 Mac 上的 tssh

使用 SOCKS5 代理时，不能继续使用太旧的 tssh。通过 ProxyCommand 支持 UDP 模式后续连接的版本至少应为支持该功能的版本；本文实测使用 0.1.27：

brew install trzsz-ssh
brew upgrade trzsz-ssh
brew link --overwrite trzsz-ssh
tssh --version

如果输出仍然是旧版本，检查命令位置：

which tssh
ls -l "$(which tssh)"

官方文档中的 UDP 配置项包括 UdpMode、TsshdPort、TsshdPath 和 UdpProxyMode：tssh UDP 配置。

九、写入 SSH 配置并自动进入 tmux

编辑 Mac 的 ~/.ssh/config，加入下面完整配置：

Host us146
    HostName 203.0.113.10
    Port 2222
    User root

    IdentityFile ~/.ssh/tssh_target_ed25519
    IdentitiesOnly yes

    ProxyCommand nc -x 10.0.0.6:1080 -X 5 %h %p

    RequestTTY force
    RemoteCommand tmux -u new-session -A -s jay '/bin/bash -l'

    # tssh 扩展配置：#!! 对 OpenSSH 来说仍是注释，对 tssh 会生效
    #!! UdpMode yes
    #!! UdpProxyMode TCP
    #!! TsshdPort 61001
    #!! TsshdPath /usr/local/bin/tsshd

之后不需要每次输入一长串参数，直接运行：

tssh us146

这条命令的工作顺序是：

  1. nc 通过内网 sing-box 的 SOCKS5 建立 TCP 引导。
  2. tssh 使用公钥登录服务器的 2222 端口。
  3. tssh 在服务器上启动 /usr/local/bin/tsshd。
  4. 新版本 tssh 继续通过 ProxyCommand 建立后续传输。
  5. 远程执行 tmux：存在 jay 会话就接入，不存在就创建。

如果不需要 tmux，可以临时覆盖远程命令：

tssh us146 -o RemoteCommand='bash -l'

十、常见报错

lookup 你的公网IP: no such host

命令里还保留着教程占位符。把 你的公网IP 换成真实 IP 或域名。

dial tcp ...:2222: i/o timeout

这是直连测试，没有经过 SOCKS5。应该使用：

nc -v -x 10.0.0.6:1080 -X 5 203.0.113.10 2222

Permission denied (publickey)

网络已经到达 SSH 服务，但服务器没有接受当前公钥。检查：

ssh -vvv -i ~/.ssh/tssh_target_ed25519 \
  -o IdentitiesOnly=yes \
  -o 'ProxyCommand=nc -x 10.0.0.6:1080 -X 5 %h %p' \
  -p 2222 root@203.0.113.10

同时确认服务器端 authorized_keys 的权限是 600，父目录权限是 700。

能进入 root，但随后 connection lost

优先检查三件事：

  1. Mac 上的 tssh 是否太旧；
  2. 服务器是否同时放行了 TCP 和 UDP 61001；
  3. tssh 配置是否包含 ProxyCommand 和 UdpProxyMode TCP。

如果只想测试原生 UDP，可以把配置临时改成：

#!! UdpProxyMode UDP

但原生 UDP 需要本机到服务器的 UDP 路径稳定；如果网络只允许代理后的 TCP，就使用 TCP。

recv auth packet failed: EOF

通常表示客户端已经进入 tsshd 阶段，但到 tsshd 端口的代理连接被服务端防火墙丢弃。确认 TCP 61001 已放行，并确认服务器上的 tsshd 路径正确：

/usr/local/bin/tsshd --version
sudo nft list ruleset | grep 61001

十一、安全收尾

  • 不要把私钥、密码、真实公网 IP、内网地址和完整 SSH 配置发布到公开博客。

  • SOCKS5 只监听内网，不要暴露到公网。

  • 服务器关闭 PasswordAuthentication 和 KbdInteractiveAuthentication。

  • 私钥最好设置口令：

    ssh-keygen -p -f ~/.ssh/tssh_target_ed25519

  • 文章中使用的 203.0.113.10 是文档示例地址，实际部署时替换成自己的目标地址。

  • tsshd 解决的是 SSH 传输稳定性和网络路径问题，不会替代服务器补丁、防火墙、最小权限和密钥管理。

总结

当服务器的公网 TCP 被阻断，但你仍然可以通过网页 VNC 或其他代理路径进入时，推荐按下面顺序处理：

网页 VNC
  → 安装 tsshd
  → 开启备用 SSH 端口 2222
  → 放行 TCP/UDP 61001
  → 配置公钥登录
  → 内网 sing-box 提供 SOCKS5
  → Mac 升级 tssh
  → ProxyCommand + UdpProxyMode TCP
  → 自动进入 tmux

最终日常使用只需要：

tssh us146
