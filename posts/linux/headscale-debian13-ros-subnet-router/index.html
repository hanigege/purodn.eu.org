Debian 13 部署 Headscale：RouterOS 端口转发与内网子网路由完整教程

从 Debian 13、Docker、Headscale、Headscale UI、Nginx Proxy Manager 到 RouterOS IPv4 端口转发，搭建可从外网访问家庭内网的自建 Tailscale 控制服务器。

本文从零搭建一套外网接入家庭内网的服务：Debian 13 VM 运行 Headscale、Headscale UI 和 Tailscale 子网路由器；RouterOS 转发必需端口；Nginx Proxy Manager（NPM）提供 HTTPS 反向代理。接入的设备可访问家庭 LAN 的 IPv4 网段。

示例采用动态公网 IPv4；运营商封锁 WAN TCP 80/443，所以控制服务使用 TCP 12335。文中的域名、IP、用户名和 MAC 都是示例值，必须替换成自己的。文章不包含真实密钥、密码或私钥。

一、先理解网络结构和端口#

项目示例值说明
家庭 LAN192.168.10.0/24换成自己的网段
RouterOS LAN 地址192.168.10.1示例网关
Headscale VM192.168.10.20建议做 DHCP 静态租约
NPM192.168.10.8已有服务沿用原地址
DDNSvpn.example.comDNS 只发布 A 记录
HTTPS 控制入口TCP 12335公网转发到 NPM
DERP/STUNUDP 3479公网转发到 Headscale VM
Tailscale 直连UDP 41641公网转发到 Headscale VM（WireGuard 监听端口）
Headscale APITCP 8080NPM 的内网 upstream
Headscale UITCP 9443只供内网 NPM 访问
外部设备 HTTPS/TCP 12335 → RouterOS → NPM:12335 → Headscale:8080
外部设备 STUN/UDP 3479 ──────────→ RouterOS → Headscale VM:3479
外部设备 WireGuard/UDP 41641 ───→ RouterOS → Headscale VM:41641
外部 Tailscale 设备 → Tailnet → Debian 子网路由器 → 192.168.10.0/24

如果 RouterOS 已有 TCP 12335 转发到 NPM，保留它，不要重复添加或改指 Headscale VM。本文新增两条转发：UDP 3479（DERP/STUN）和 UDP 41641（Tailscale 直连）。只宣告家庭 IPv4 LAN，不宣告 LAN IPv6，也不给 DDNS 加 AAAA 记录；Tailnet 自己的 ULA IPv6 不等于把家庭公网 IPv6 子网路由出去。

二、准备 DDNS、证书和固定 VM 地址#

域名服务商上确认 DDNS 客户端更新 A 记录：

名称：vpn
类型：A
记录值：家中 RouterOS 当前公网 IPv4

不要给这个主机名添加 AAAA。可检查解析：

dig +short A vpn.example.com
dig +short AAAA vpn.example.com

第一条应返回当前公网 IPv4，第二条无输出。没有 dig 时执行：

sudo apt update
sudo apt install -y dnsutils

还没有 DDNS 时，最省事的做法是用 RouterOS 自带的 IP Cloud（免费、由路由器本人更新，最适合动态公网 IP）：

/ip cloud set ddns-enabled=yes update-time=yes
/ip cloud print

记下输出的 dns-name（形如 xxxxxxxx.sn.mynetname.net），再到域名服务商处给 vpn 加一条 CNAME 记录指向它。这样公网 IP 变化时，vpn.example.com 会跟着更新；用 dig 检查时看到 CNAME 最终解析到当前公网 IPv4 即正确。若域名服务商提供 API，也可以写 RouterOS 脚本加计划任务直接更新 A 记录，各家 API 不同，本文不展开。

NPM 申请证书使用 DNS-01 Challenge。WAN 的 80/443 被封不影响 DNS-01 验证；不要选需要外部 TCP 80 的 HTTP-01。

给 PVE 中的 Debian VM 固定 IP。建议在 RouterOS 将 DHCP 租约改成静态：先让 VM 启动并拿到租约，再确认 MAC、IP 未被占用：

/ip dhcp-server lease print detail
/ip dhcp-server print detail
/ip arp print

替换示例 MAC 和 IP 后执行：

/ip dhcp-server lease make-static [find where mac-address="AA:BB:CC:DD:EE:FF"]
/ip dhcp-server lease set [find where mac-address="AA:BB:CC:DD:EE:FF"] address=192.168.10.20 comment="headscale-vm"
/ip dhcp-server lease print detail where mac-address="AA:BB:CC:DD:EE:FF"

建议 VM 至少 2 vCPU、2 GB RAM、16 GB 磁盘，网卡连接家庭 LAN bridge。不要在 Debian 和 RouterOS 同时设置相冲突的静态 IP。

三、RouterOS 配置端口转发#

本节适用于 RouterOS v7，并假定 WAN/LAN interface list 已配好。先确认当前登录的是接收公网 IPv4 的主路由。不要假设 ether1 一定是 WAN，不要重置现有防火墙。

1. 备份并检查已有规则#

WinBox 建议先进入 Safe Mode（终端按 Ctrl+X），然后备份：

/export terse file=before-headscale
/system backup save name=before-headscale
/interface list print
/interface list member print detail
/ip address print detail
/ip route print detail
/ip firewall nat print detail
/ip firewall filter print detail where chain=forward
/ip service print

若 WAN/LAN interface list 名称不同，按实际名称改下面命令。检查 TCP 12335：

/ip firewall nat print detail where protocol=tcp and dst-port=12335

已有规则正确指向 NPM 时保留它。若没有，替换 NPM 内网地址后才添加：

/ip firewall nat add chain=dstnat action=dst-nat in-interface-list=WAN dst-address-type=local protocol=tcp dst-port=12335 to-addresses=192.168.10.8 to-ports=12335 comment="Headscale-via-NPM-TCP12335" place-before=0

这是公网 TCP 12335 到 NPM 的规则，不是到 Headscale VM。若 NPM 用 Docker，通常宿主机 12335 映射到容器 443。

2. 将 UDP 3479 转发给 Headscale VM#

先检查是否已有同端口规则：

/ip firewall nat print detail where protocol=udp and dst-port=3479

确认没有重复项，替换 VM 地址后添加：

/ip firewall nat add chain=dstnat action=dst-nat in-interface-list=WAN dst-address-type=local protocol=udp dst-port=3479 to-addresses=192.168.10.20 to-ports=3479 comment="Headscale-STUN-UDP3479" place-before=0

不要转发 Tailscale 的整个 UDP 端口范围，也不要把 UI 9443 转发到公网。

3. 将 UDP 41641 转发给 Headscale VM#

41641 是 Tailscale 的 WireGuard 监听端口。外部设备与子网路由器建立直连时，第一个握手包必须能从公网打到 VM 的 41641/udp；缺了这条转发，双方只能经 DERP 中继通信——能通，但延迟高、速度慢、稳定性差。先检查是否已有同端口规则：

/ip firewall nat print detail where protocol=udp and dst-port=41641

确认没有重复项，替换 VM 地址后添加：

/ip firewall nat add chain=dstnat action=dst-nat in-interface-list=WAN dst-address-type=local protocol=udp dst-port=41641 to-addresses=192.168.10.20 to-ports=41641 comment="Headscale-Direct-UDP41641" place-before=0

4. 确认 forward filter 放行 DNAT 流量#

先查看完整的 forward 规则和顺序：

/ip firewall filter print detail where chain=forward

常见 RouterOS 防火墙已有允许 dstnat 流量的规则。如果确实没有，且有 WAN drop，则添加两条只匹配目标服务的窄规则。把地址换成自己的 NPM 和 Headscale VM 地址：

/ip firewall filter add chain=forward action=accept in-interface-list=WAN out-interface-list=LAN protocol=tcp dst-address=192.168.10.8 dst-port=12335 connection-state=new connection-nat-state=dstnat comment="Allow-Headscale-NPM-TCP12335" place-before=0
/ip firewall filter add chain=forward action=accept in-interface-list=WAN out-interface-list=LAN protocol=udp dst-address=192.168.10.20 dst-port=3479 connection-state=new connection-nat-state=dstnat comment="Allow-Headscale-STUN-UDP3479" place-before=0
/ip firewall filter add chain=forward action=accept in-interface-list=WAN out-interface-list=LAN protocol=udp dst-address=192.168.10.20 dst-port=41641 connection-state=new connection-nat-state=dstnat comment="Allow-Headscale-Direct-UDP41641" place-before=0

place-before=0 将窄规则放在链首，避免落到后面的 WAN drop；匹配条件仍限定 WAN、LAN、协议、目标地址/端口以及 dstnat。若有自定义防火墙，先审查顺序，勿粘贴通用整套规则。

检查规则及计数：

/ip firewall nat print stats where comment~"Headscale"
/ip firewall filter print stats where comment~"Headscale"
/ip firewall nat print detail where dst-port=12335

最后一条不是必须，可省略；以 NAT/filter 的命中计数为准。外部测试后计数应增加。若上游还有光猫/路由器 NAT，需在实际持有公网 IPv4 的设备上做 DNAT，或让上游继续转发端口。不要把动态公网 IP 写死到 NAT 规则中。

五、部署 Headscale 服务#

创建配置文件，把示例域名换成自己的：

cat > /opt/headscale/config/config.yaml <<'EOF'
server_url: https://vpn.example.com:12335
listen_addr: 0.0.0.0:8080
metrics_listen_addr: 127.0.0.1:9090
grpc_listen_addr: 127.0.0.1:50443
grpc_allow_insecure: false
noise:
  private_key_path: /var/lib/headscale/noise_private.key
prefixes:
  v4: 100.64.0.0/10
  v6: fd7a:115c:a1e0::/48
  allocation: sequential
derp:
  server:
    enabled: true
    region_id: 999
    region_code: home
    region_name: Home DERP
    verify_clients: true
    stun_listen_addr: "0.0.0.0:3479"
    private_key_path: /var/lib/headscale/derp_server_private.key
    automatically_add_embedded_derp_region: true
  urls:
    - https://controlplane.tailscale.com/derpmap/default
  paths: []
  auto_update_enabled: true
  update_frequency: 3h
database:
  type: sqlite
  sqlite:
    path: /var/lib/headscale/db.sqlite
    write_ahead_log: true
log:
  level: info
  format: text
dns:
  magic_dns: false
  override_local_dns: true
  search_domains: []
  nameservers:
    global:
      - 192.168.10.1
unix_socket: /var/run/headscale/headscale.sock
unix_socket_permission: "0770"
EOF

上面 dns 一节只影响接受 Tailscale DNS 的客户端（手机 App 默认接受）：它们的 DNS 会被指到 global 里填的内网 DNS（示例是 RouterOS 本人），人在外面也能解析内网主机名。子网路由器和本文的 Linux 客户端都带 –accept-dns=false，不受它影响。global 不要填公网 DNS，否则内网域名会被送到外面解析、也解析不到内网主机。

创建 Compose 文件并启动：

cat > /opt/headscale/compose.yaml <<'EOF'
services:
  headscale:
    image: ghcr.io/juanfont/headscale:0.29.5
    container_name: headscale
    command: serve
    restart: unless-stopped
    volumes:
      - ./config:/etc/headscale
      - ./data:/var/lib/headscale
    ports:
      - "192.168.10.20:8080:8080/tcp"
      - "192.168.10.20:3479:3479/udp"
EOF
cd /opt/headscale
docker compose -f compose.yaml config
docker compose -f compose.yaml up -d
docker compose -f compose.yaml ps
docker logs --tail=100 headscale
ss -lunp | grep ':3479'

Headscale 会自动在 data 目录生成数据库和密钥，不要手工创建空数据库，也不要删除 /opt/headscale/data。端口只绑 VM 的内网地址：8080 是给 NPM 的 upstream，3479 的公网入口只由 RouterOS 转发控制，不要再从别处把它们映射到公网。

六、配置 NPM 反向代理与 UI 路径#

在 NPM 新建/修改 Proxy Host：

  1. Domain Names：vpn.example.com。
  2. Scheme：HTTP；Forward Hostname/IP：Headscale VM 内网地址；Forward Port：8080。
  3. 启用 Websockets Support。
  4. SSL 选择该域名有效证书，启用 Force SSL。80/443 入站封锁时使用 DNS Challenge 申请证书，不选 HTTP-01。
  5. NPM 公网 HTTPS 监听 TCP 12335；若用 Docker，常见宿主机端口 12335 映射到容器 443。RouterOS 已有 TCP 12335 仍指向 NPM。

还没有这个域名的证书时，先在 NPM 的 SSL Certificates 里 Add Certificate → Let’s Encrypt：Domain Names 填 vpn.example.com，打开 Use a DNS Challenge，在 DNS Provider 选自己的域名服务商并粘贴它的 API 凭据，同意条款后保存；签发成功再回 Proxy Host 的 SSL 里选这张证书。若 NPM 用 Docker 且宿主机还没有 12335 监听，需要在 NPM 自己的 compose 里给它加一条 “12335:443” 端口映射并重建 NPM 容器，宿主机才会对外提供 12335 的 HTTPS。

Headscale UI 走相同域名的 /web/，避免 CORS。在该 Proxy Host 的 Advanced 配置中加入以下 Nginx location，并换成自己的 LAN 和 VM 地址：

location ^~ /web/ {
    allow 192.168.10.0/24;
    allow 100.64.0.0/10;
    deny all;
    proxy_pass http://192.168.10.20:9443/web/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

七、启动 Headscale UI 并配置 99 年 API key#

启动 UI 容器：

mkdir -p /opt/headscale-ui
cd /opt/headscale-ui
cat > compose.yaml <<'EOF'
services:
  headscale-ui:
    image: ghcr.io/gurucomputing/headscale-ui:latest
    container_name: headscale-ui
    restart: unless-stopped
    ports:
      - "192.168.10.20:9443:8080/tcp"
EOF
docker compose config
docker compose up -d
docker compose ps
docker logs --tail=100 headscale-ui

9443 仅供 LAN 中的 NPM 访问，不在 RouterOS 做公网转发。创建用户并生成 99 年 key：

docker exec headscale headscale users create home
docker exec headscale headscale users list
docker exec headscale headscale apikeys create --expiration 99y

打开 https://vpn.example.com:12335/web/ 的 Settings：

  1. Headscale URL 填 https://vpn.example.com:12335，不要加 /web/。
  2. Headscale API Key 粘贴命令输出的完整 key。
  3. 点 Save API Key，再点 Test Server Settings。

终端的 key 只保存在密码管理器，不要公开。UI 会将 key 存进浏览器 localStorage。输入框显示圆点是遮罩效果，圆点数量不一定等于 key 长度；不要输入自己手打的星号代替真实 key。若测试失败，检查完整 key、域名/端口、TLS 证书和是否通过同域 /web/ 打开。

八、配置 Tailscale IPv4 子网路由器#

启用 IPv4 转发：

cat > /etc/sysctl.d/99-tailscale-router.conf <<'EOF'
net.ipv4.ip_forward = 1
net.ipv4.conf.all.src_valid_mark = 1
EOF
sysctl --system
sysctl net.ipv4.ip_forward net.ipv4.conf.all.src_valid_mark

创建短时预授权 key，命令输出只用于首次注册：

docker exec headscale headscale preauthkeys create --user home --expiration 1h

在本机临时保存 key（替换等号后的说明文字为真实输出，不要分享它）：

mkdir -p /opt/tailscale-gateway/state
cd /opt/tailscale-gateway
umask 077
cat > .env <<'EOF'
TS_AUTHKEY=把刚生成的预授权key粘贴到这里
EOF
chmod 600 .env
grep '^TS_AUTHKEY=' .env

grep 的输出应以 TS_AUTHKEY=tskey-auth- 开头。若显示的还是那句中文说明文字，说明 key 没替换进去，容器注册会失败（日志会出现 auth key 无效一类报错），先改对再往下走。

创建 Compose 文件：

cat > compose.yaml <<'EOF'
services:
  tailscale:
    image: ghcr.io/tailscale/tailscale:stable
    container_name: tailscale
    hostname: subnet-router
    network_mode: host
    restart: unless-stopped
    devices:
      - /dev/net/tun:/dev/net/tun
    cap_add:
      - NET_ADMIN
      - NET_RAW
    environment:
      TS_AUTHKEY: $TS_AUTHKEY
      TS_STATE_DIR: /var/lib/tailscale
      TS_AUTH_ONCE: "true"
      TS_USERSPACE: "false"
      TS_ROUTES: 192.168.10.0/24
      TS_EXTRA_ARGS: --login-server=https://vpn.example.com:12335 --accept-dns=false
    volumes:
      - ./state:/var/lib/tailscale
EOF
docker compose config
docker compose up -d
docker compose ps
docker logs --tail=100 tailscale

把 TS_ROUTES 和域名换成自己的。首次注册成功后，从 Compose 删除 TS_AUTHKEY 行，删掉临时 .env 并重建容器；state/ 保留节点身份：

cd /opt/tailscale-gateway
sed -i '/TS_AUTHKEY:/d' compose.yaml
rm -f .env
docker compose up -d --force-recreate
docker exec tailscale tailscale status
docker exec tailscale tailscale ip -4

Docker nftables 转发修复（仅在发现该故障时执行）#

若 Tailnet 到 gateway 自身通，但访问 LAN 超时，检查 iptables 后端与 DOCKER-USER：

iptables --version
iptables-legacy -S FORWARD 2>/dev/null || true
iptables-nft -S DOCKER-USER

若确认 Docker nft FORWARD 拦截子网转发，下面两条只放行 Tailnet IPv4 段到指定 LAN，以及 LAN 回给 Tailnet 的已建立连接。替换 LAN CIDR；接口名按 ip -br link 的实测改：tailscale0 是 Tailscale 的接口，后一个是 VM 的 LAN 网卡（常见 eth0，PVE 里也可能是 ens18）：

iptables-nft -C DOCKER-USER -i tailscale0 -o eth0 -s 100.64.0.0/10 -d 192.168.10.0/24 -m comment --comment "Headscale-subnet-forward" -j ACCEPT 2>/dev/null || iptables-nft -I DOCKER-USER 1 -i tailscale0 -o eth0 -s 100.64.0.0/10 -d 192.168.10.0/24 -m comment --comment "Headscale-subnet-forward" -j ACCEPT
iptables-nft -C DOCKER-USER -i eth0 -o tailscale0 -s 192.168.10.0/24 -d 100.64.0.0/10 -m conntrack --ctstate ESTABLISHED,RELATED -m comment --comment "Headscale-subnet-return" -j ACCEPT 2>/dev/null || iptables-nft -I DOCKER-USER 2 -i eth0 -o tailscale0 -s 192.168.10.0/24 -d 100.64.0.0/10 -m conntrack --ctstate ESTABLISHED,RELATED -m comment --comment "Headscale-subnet-return" -j ACCEPT
iptables-nft -nvL DOCKER-USER --line-numbers

使规则在 Docker 重启后恢复：

cat > /usr/local/sbin/headscale-subnet-forwarding.sh <<'EOF'
#!/bin/sh
set -eu
IPT=/usr/sbin/iptables-nft
$IPT -w -C DOCKER-USER -i tailscale0 -o eth0 -s 100.64.0.0/10 -d 192.168.10.0/24 -m comment --comment "Headscale-subnet-forward" -j ACCEPT 2>/dev/null || $IPT -w -I DOCKER-USER 1 -i tailscale0 -o eth0 -s 100.64.0.0/10 -d 192.168.10.0/24 -m comment --comment "Headscale-subnet-forward" -j ACCEPT
$IPT -w -C DOCKER-USER -i eth0 -o tailscale0 -s 192.168.10.0/24 -d 100.64.0.0/10 -m conntrack --ctstate ESTABLISHED,RELATED -m comment --comment "Headscale-subnet-return" -j ACCEPT 2>/dev/null || $IPT -w -I DOCKER-USER 2 -i eth0 -o tailscale0 -s 192.168.10.0/24 -d 100.64.0.0/10 -m conntrack --ctstate ESTABLISHED,RELATED -m comment --comment "Headscale-subnet-return" -j ACCEPT
EOF
chmod 0755 /usr/local/sbin/headscale-subnet-forwarding.sh
cat > /etc/systemd/system/headscale-subnet-forwarding.service <<'EOF'
[Unit]
Description=Allow Headscale subnet forwarding through Docker
Requires=docker.service
After=docker.service
PartOf=docker.service
[Service]
Type=oneshot
ExecStart=/usr/local/sbin/headscale-subnet-forwarding.sh
RemainAfterExit=yes
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl enable --now headscale-subnet-forwarding.service
systemctl status headscale-subnet-forwarding.service --no-pager
iptables-nft -nvL DOCKER-USER --line-numbers

若 DOCKER-USER 不存在，先确认 Docker 正常启动、Tailscale 用 host network、iptables 后端判断正确。不要清空规则或关闭防火墙作为绕过办法。

九、批准子网路由#

找到 subnet-router 的节点 ID：

docker exec headscale headscale nodes list

把 <节点ID> 替换成实际数字：

docker exec headscale headscale nodes approve-routes --identifier <节点ID> --routes 192.168.10.0/24
docker exec headscale headscale nodes list-routes

也可在 UI 的 Device View 启用路由。必须批准/启用，节点仅宣告而未获批准时，客户端仍无法访问 LAN。

十、手机和电脑客户端注册#

客户端自定义控制服务器填写：

https://vpn.example.com:12335

手机/桌面客户端会显示带一次性 auth-id 的注册命令。在 Headscale VM 上执行，替换 auth ID 和用户名：

docker exec headscale headscale auth register --auth-id '<客户端显示的auth-id>' --user home

回客户端点重试/继续。Linux 客户端安装及登录命令：

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --login-server=https://vpn.example.com:12335 --accept-routes --accept-dns=false

Linux 必须接受子网路由（–accept-routes）；Windows、macOS、iOS、Android 在路由获批后会自动使用，不用设置。若 iOS 上连上了 Tailnet 却访问不到 LAN，先把 Tailscale App 升到最新版，再在 App 设置里确认 Use Subnet Routes 已打开。Device View 应能看到新节点及其 Tailnet IPv4 地址。

十一、外网端到端验证#

在 Headscale VM 检查服务、节点和路由：

docker compose -f /opt/headscale/compose.yaml ps
docker exec headscale headscale nodes list
docker exec headscale headscale nodes list-routes
docker exec tailscale tailscale status
docker exec tailscale tailscale debug derp-map

再确认外部节点与子网路由器之间是直连而不是中继（IP 换成上一步 nodes list 里手机节点的 Tailnet IPv4）：

docker exec tailscale tailscale ping 100.64.0.2

输出里出现 direct 说明直连已建立；出现 via DERP 说明还在走中继——能用，但慢且不稳，按第十二节第 6 条查 41641 转发。

关闭手机 Wi-Fi，用蜂窝网络连接 Tailnet，再访问 LAN 中真实存在的服务：

curl -v --connect-timeout 5 http://192.168.10.8:81/
nc -vz -w 5 192.168.10.30 22

把 IP 和端口替换成自己的设备。HTTP 200 或 TCP succeeded 表示端到端路径通。UDP 不可用普通 TCP 检查工具判断；结合客户端状态、DERP map 和服务日志检查。

十二、排查顺序#

  1. 客户端连不上控制端：核对 DDNS A 记录、TCP 12335 → NPM、NPM upstream VM:8080、证书和 server_url。
  2. UI API key 测试失败：用同域名 /web/ 访问，Headscale URL 不带 /web/，确认复制了完整 key。
  3. Connected 但 LAN 超时：核对子网路由宣告和批准、客户端 accept routes、Linux ip_forward、DOCKER-USER 网段和计数。
  4. 外部端口不通：检查双重 NAT、RouterOS WAN list、NAT/filter 命中计数、运营商 UDP 3479 限制。
  5. 不要关闭防火墙或清空 NAT/filter；逐条核对目标地址、端口和规则顺序，避免影响其它服务。
  6. 能连通但明显慢、延迟高：多半在走 DERP 中继。tailscale ping 看是 direct 还是 via DERP；若是中继，依次查 RouterOS 的 UDP 41641 转发与命中计数、VM 上 41641/udp 是否在监听（ss -lunp | grep 41641）、运营商是否限制该端口。

十三、备份与维护#

/opt/headscale/data 里有数据库和 noise、DERP 私钥，丢了等于所有节点身份作废、全部设备要重新注册。搭好后把三个目录整包备份一份，并放到 VM 之外保存：

tar czf /root/headscale-backup-$(date +%F).tgz -C /opt headscale headscale-ui tailscale-gateway

升级时注意：Headscale 镜像在 Compose 里固定为 0.29.5，升级先备份、再改标签，并看 changelog 里有没有配置格式变化；Tailscale 镜像用的是浮动的 stable 标签，docker compose pull 就可能换版本，在意可复现时可以在验证后把标签换成具体版本号。
